```python
def seed_to_angles(seed: str, num_angles: int = 3) -> List[float]:
    """Convert 128-bit seed to quantum rotation angles in [0, 2π]"""
    angles = []
    for i in range(num_angles):
        hash_input = f"{seed}:angle_{i}".encode()
        hash_output = hashlib.sha256(hash_input).digest()
        byte_value = int.from_bytes(hash_output[:8], byteorder='big')
        normalized = (byte_value % (2**32)) / (2**32)
        angle = normalized * 2 * np.pi
        angles.append(angle)
    return angles
```

# Local WebSocket Bridge Architecture for Reality/OS

## Recommendation

The Android companion should host the local bridge server. Reality/OS connects to it as a WebSocket client, while the Android app remains the only component allowed to call Android WiFi and Bluetooth APIs. The bridge should expose **capabilities, discovery, telemetry, and explicitly authorized commands** rather than exposing raw Android APIs.

The first release should be **read-only by default**. Scanning, connecting, and disconnecting may be enabled as individual capabilities. Device writes, characteristic writes, network changes, and other consequential actions should require an explicit operator action and a short-lived command authorization.

The existing Reality/OS interface already communicates this posture through its “observing” state, event stream, and consent firewall. The bridge should preserve that model at the protocol level.

## Two viable connection models

| Approach | Tradeoffs | Cost | Setup complexity |
|---|---|---:|---:|
| **Android-hosted local WebSocket server** | Lowest latency and no cloud dependency. Works best when the ROS page is opened on the Android device or served from a trusted local origin. Desktop-to-phone connections require careful HTTPS/WSS handling. | Free beyond development time | Medium |
| **Android bridge client plus small local desktop agent** | The Android app connects outbound to a local agent. The browser connects to the agent over `localhost`, avoiding most LAN discovery and mixed-content problems. Adds a second process to install and maintain. | Free if distributed as an app; higher maintenance | High |
| **Paired relay using WSS** | Works from any browser and across networks. The relay must be secured, authenticated, and designed so that radio commands cannot be forged. It is no longer strictly local and introduces hosting and privacy considerations. | Hosting and operations cost | High |

The recommended implementation is the first model for the local release, with a relay-compatible protocol so the third option can be added later without changing the ROS UI.

## System topology

```text
+---------------------------+       WebSocket        +-----------------------------+
| Reality/OS browser client | <--------------------> | Android BridgeService       |
| - renders telemetry       |                         | - owns bridge session       |
| - displays capabilities   |                         | - owns WiFi/BLE permissions  |
| - asks for commands       |                         | - validates commands        |
| - never holds radio APIs  |                         | - emits telemetry/events    |
+---------------------------+                         +---------------+-------------+
                                                                        |
                                                        +---------------+-------------+
                                                        | Android platform APIs       |
                                                        | WifiManager / BLE scanner   |
                                                        | BluetoothGatt / permissions |
                                                        +-----------------------------+
```

The Android service should not expose the underlying `BluetoothGatt`, `WifiManager`, or scan callbacks directly. It should translate them into a small stable domain model. This makes the web client independent of Android API changes and prevents the browser from becoming a privileged controller.

## Lifecycle and discovery

`BridgeService` should be a foreground service while a bridge session is active. The service should start only after the user presses **Start local bridge** in the Android app. Its notification should show the listening state, paired browser count, and a stop action.

The service should bind to a loopback or LAN socket according to the selected mode:

- **Same-device mode:** bind to `127.0.0.1` on a fixed port such as `8765`. This is the simplest and safest mode when Reality/OS is opened in Android Chrome or inside a local wrapper.
- **Local-network mode:** bind to the Android WiFi interface and advertise `_realityos._tcp` through Android Network Service Discovery. Require the operator to approve a displayed pairing code before accepting a browser session.
- **Relay mode later:** do not expose the local port publicly. Establish an outbound authenticated connection to a relay and reuse the same message protocol.

Android Network Service Discovery is appropriate for finding a service on the same local network.[3] It should be treated as discovery only, not authentication. A discovered service must still require pairing.

The browser should attempt connection in this order:

1. A manually entered `ws://127.0.0.1:8765` endpoint.
2. A previously paired local endpoint stored only in browser storage.
3. A discovered endpoint supplied by an Android pairing screen.
4. A future `wss://` relay endpoint.

A hosted HTTPS page cannot safely assume that an arbitrary `ws://192.168.x.x` endpoint will be accepted by every browser. For the first local release, target same-device localhost mode or serve the ROS UI from the same trusted local bridge origin. For desktop-to-phone control, use WSS with a trusted certificate or introduce the local desktop agent option.

## Pairing and security

The bridge should use **application-layer pairing**, even on a home network. The minimum flow is:

1. Android starts the bridge and displays a six-digit pairing code plus a short expiry, for example five minutes.
2. Reality/OS connects to the discovered endpoint and sends a `pair.request` containing the code.
3. Android verifies the code, generates a random session token, and returns `pair.accepted`.
4. The browser stores the token for that origin only. The Android app stores a hash of the token, not the token itself.
5. Every subsequent message includes the session token and a monotonically increasing request identifier.
6. Android expires the token when the user stops the bridge, revokes the browser, or the inactivity timer elapses.

For a stronger second iteration, use an ephemeral public-key handshake. The browser creates a key pair, Android displays a short fingerprint, and the operator confirms the fingerprint on both screens. This prevents a malicious device on the same LAN from impersonating the bridge after the initial discovery step.

The bridge must also enforce:

- Origin allowlisting for the ROS application.
- One active operator session by default.
- A maximum message size, command rate, and scan duration.
- No unauthenticated control messages.
- No secrets in URLs, browser logs, or event payloads.
- Explicit revocation and a visible Android stop control.
- A default-deny command policy.

Use JSON for the first version because it is easy to inspect in development and maps directly to the ROS event stream. Every message should use the same envelope:

```json

  "timestamp": "2026-09-20T09:30:00Z",
  "session": "session_token",
  "payload": {
    "durationMs": 8000
  }
}
```

Responses should correlate by `id`:

```json
  "timestamp": "2026-09-20T09:30:00.042Z",
```

## Initial message types

The first release should implement the following types.

| Type | Direction | Purpose |
|---|---|---|
| `hello` | Browser → Android | Negotiate protocol version and requested features |
| `bridge.info` | Android → Browser | Report bridge identity, Android version, and current posture |
| `capabilities.get` | Browser → Android | Request the current permission and feature matrix |
| `capabilities.state` | Android → Browser | Return read, scan, connect, and write capabilities |
| `pair.request` | Browser → Android | Submit the human-approved pairing code |
| `pair.accepted` | Android → Browser | Return the short-lived session state |
| `wifi.scan.start` | Browser → Android | Request a bounded WiFi scan |
| `wifi.scan.result` | Android → Browser | Stream sanitized access-point results |
| `ble.scan.start` | Browser → Android | Request a bounded BLE scan |
| `ble.scan.result` | Android → Browser | Stream sanitized BLE advertisements |
| `ble.connect.request` | Browser → Android | Request a user-visible BLE connection |
| `ble.connection.state` | Android → Browser | Report connecting, connected, disconnected, or failed |
| `ble.read.request` | Browser → Android | Read a declared characteristic |
| `ble.write.prepare` | Browser → Android | Present a write for operator review; do not execute it |
| `ble.write.commit` | Browser → Android | Execute an already approved write with a short-lived approval ID |
| `bridge.event` | Android → Browser | Send permission, radio, and lifecycle events |
| `bridge.stop` | Browser → Android | Ask Android to close the browser session, never to shut down silently |

WiFi scan results should omit unnecessary data and should not expose saved-network credentials. BLE results should include a stable device identifier, display name when available, RSSI, service UUIDs, and timestamp. Manufacturer data should be opt-in because it can contain identifying information.

## Write authorization

Writes are the highest-risk operation and should not be implemented in the same milestone as discovery. When implemented, use a two-step flow:

1. The browser sends `ble.write.prepare` with the device ID, service UUID, characteristic UUID, and bytes encoded as base64.
2. Android validates the target and displays a confirmation containing the device, characteristic, byte length, and a human-readable description when available.
3. Android returns an `approvalId` that expires after 30 seconds and can be used exactly once.
4. The browser sends `ble.write.commit` with that `approvalId`.
5. Android performs the write and emits the result.

The browser must never be able to turn a generic string into an arbitrary write without showing the exact bytes and target. The Android app remains the final authority.

## Android implementation shape

Because the current Android source directory is not available in this session, the following names are insertion points rather than edits to existing classes:

```text
app/src/main/java/.../bridge/
  BridgeService.java       // foreground lifecycle and session ownership

  PairingManager.java      // short-lived codes and session tokens
```

The existing WiFi and BLE helpers should remain the platform adapters. `CommandRouter` should call those helpers and convert their callbacks into protocol events. It should not contain UI code. Android permission prompts must be initiated from an Activity or a user-approved flow, not unexpectedly from a background WebSocket message.

For Android 12 and newer, the app must request the appropriate Bluetooth runtime permissions and declare them in the manifest.[2] The bridge should report missing permissions through `capabilities.state` rather than repeatedly triggering permission prompts.
